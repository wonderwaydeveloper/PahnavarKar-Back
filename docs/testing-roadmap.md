## هدف و تعریف «تست کامل»

این برنامه برای پوشش رفتارهای بک‌اند موجود در نقشهٔ راه و کد فعلی است؛ هدف آن تولید تست صوری برای هر فایل یا پوشاندن خطوط بدون سنجش رفتار نیست.

**مرز scope:** این سند کل سرور Laravel را پوشش می‌دهد: API، صفحات و actionهای وب‌پنل، jobs، commands، scheduler، دیتابیس، پاسخ خطا و قرارداد پاسخ مورد مصرف کلاینت‌ها. تست رفتار تعاملی React/Inertia در مرورگر، رابط و منطق درون Expo (کامپوننت‌ها، Context/Zustand، SecureStore و React Query)، و آزمون عملی زیرساخت production در scope PHPUnit نیستند و به تست مرورگر/کلاینت/عملیاتی جدا نیاز دارند؛ رفتار سمت سرور و قراردادهای API مصرف‌شده توسط آن‌ها در همین نقشه می‌مانند.

در این سند، «تکمیل تست‌ها» به معنی تحقق هم‌زمان این موارد است:

1. تمام قابلیت‌های در محدودهٔ بک‌اند در ماتریس پوشش ثبت شده و هر معیار پذیرش، تست خودکار متناسب داشته باشد.
2. تمام routeهای API و وب، از نظر پاسخ موفق، ورودی نامعتبر و دسترسی مجاز/غیرمجاز بررسی شوند؛ routeهای صرفاً زیرساختی و vendor با دلیل از scope خارج شوند.
3. همهٔ جریان‌های احراز هویت، مالی، دسترسی و تغییر داده، حالت موفق، شکست و حالت مرزی را پوشش دهند.
4. گزارش coverage از CI منتشر و آستانه‌ها به‌صورت خودکار enforce شوند؛ هدف کلی حداقل ۸۰٪ پوشش خطوط/دستورات برنامه است. در ماژول‌های حساس Auth، Wallet و Payments، همهٔ شاخه‌های تصمیمیِ تعریف‌شده در ماتریس تست باید تست متناظر داشته باشند. اگر درصد branch coverage به‌عنوان gate خودکار خواسته شود، CI باید driver دارای branch coverage مانند Xdebug داشته باشد؛ PCOV/Clover فعلی به‌تنهایی اثبات branch coverage نیست.
5. concurrency و قفل‌های دیتابیس روی MySQL نیز آزموده شوند؛ SQLite به‌تنهایی معیار کافی برای صحت قفل و هم‌زمانی نیست.
6. تست‌های بار K6 جدا از PHPUnit و فقط در local/staging ایمن اجرا شوند.

۱۰۰٪ پوشش خطی کل برنامه شرط تعریف‌شدهٔ این طرح نیست؛ کد چارچوب، bootstrap، adapterهای بیرونی و شاخه‌های وابسته به زیرساخت واقعی ممکن است پوشش خطی ۱۰۰٪ را نامناسب یا بی‌معنا کنند. معیار «۱۰۰٪» در این برنامه، پوشش همهٔ رفتارها و معیارهای پذیرشِ ثبت‌شده است؛ همراه با حداقل ۸۰٪ پوشش کلی کد و پوشش کامل شاخه‌های حساس مشخص‌شده. این معیار نبود هرگونه باگ را تضمین نمی‌کند.

### وضعیت بازبینی جاری — 2026-10-26

این snapshot، وضعیت تاریخی فاز صفر و ارزیابی‌های قدیمی‌تر پایین سند را به‌روزرسانی می‌کند؛ شواهد قدیمی حذف نشده‌اند. ماتریس ۶۰۰ ردیف دارد: ۲۲۹ فایل، ۹۷ route، ۲۵ بخش roadmap، ۲۱۵ requirement، ۲۵ رکورد implementation-gap و ۹ exclusion دایرکتوری. خروجی زندهٔ `php artisan route:list --json` با ۱۳۹ زوج method/path در ۷۹ URI با ماتریس تطبیق داده شد؛ action و middleware هر ۹۷ ردیف route همگام شده‌اند. این تطبیق فقط صحت inventory را ثابت می‌کند و جای تست رفتاری routeها را نمی‌گیرد. inventory فایل‌های کد با مسیرهای شناخته‌شده تطبیق شد؛ فایل‌های فونت و دیتابیس محلی با exclusionهای موجود پوشش داده شده‌اند و دو فایل `.gitignore` نیز صریحاً از تست رفتار برنامه خارج شدند.

فاز صفر هنوز بسته نیست: سیاست معماری CORS مشخص شد (پنل same-origin با Laravel/Inertia و API جدا برای اپ native)، اما تطبیق دامنه و reverse proxy به staging/پیش از انتشار موکول است؛ CORS باز یا wildcard پیکربندی نشده است. README با صفحات وب‌پنل و محدودهٔ واقعی audit نقش‌ها همگام شد. نقص rollback migration `batch_uuid` با تست قرارداد بازتولید و اصلاح شد. مسیر suspend/reactivate در `AdminUserAccountStatusTest` (۸ تست، ۵۷ assertion) و فهرست کاربران/تغییر دسترسی در `AdminUserManagementTest` (۹ تست، ۱۳۹ assertion) آزموده می‌شوند. `AdminRoleManagementTest` نیز ۱۳ تست و ۱۲۴ assertion برای دسترسی Owner/Admin/User، ماتریس مجوزهای seed، CRUD نقش/مجوز، محافظت نقش‌ها، جلوگیری از ارتقای manage roles، guard، audit و invalidation کش دارد. شکاف ممیزی تغییر نقش نیز بسته شد: command کنسولی، ثبت‌نام OTP، هر دو seeder و مسیر دسترسی پنل با ثبت صریح و تراکنشی آزموده می‌شوند؛ listener عمومی Spatie حذف شد تا به رویدادهای غیرفعال وابسته نباشد و ثبت تکراری رخ ندهد. لاگ‌های تغییرات کاربر و مدل‌های مالی/اشتراک با allowlist و آزمون حذف اطلاعات حساس پوشش داده شدند؛ ثبت دوگانهٔ listenerهای اشتراک نیز رفع شد. سیاست نگهداری activity log با SQLite موقت آزموده شد: مرز دقیق ۳۶۵ روز، فیلتر نام لاگ، خطای ورودی نامعتبر و زمان‌بندی روزانهٔ ۰۳:۰۰ UTC با قفل overlap تست شدند. بررسی اجرای واقعی scheduler، پایش production و cache مشترک چند میزبان عمداً تا زمان استقرار به تعویق افتاد و در ماتریس `staging-only` ثبت شد. در این بازبینی نقص پیاده‌سازی در CRUD نقش/مجوز مشاهده نشد و تغییر کد runtime لازم نبود. اجرای کامل PHPUnit برابر ۱۱۸ تست و ۹۹۹ assertion موفق است. lint کل مخزن به‌علت فایل‌های قدیمیِ دست‌نخورده baseline قرمز دارد؛ فایل‌های PHP تغییرکرده جداگانه اعتبارسنجی شدند. اجرای workflow/CI یا MySQL انجام نشد.

### کارها

- استخراج featureها از roadmap و تطبیق با `routes/api.php`, `routes/web.php`, middlewareها، سرویس‌ها، jobها، commandها، eventها، مدل‌ها و migrationها.
- فهرست‌کردن routeها و middleware مورد انتظار برای هر نقش: مهمان، User، Admin، Owner و کاربر غیرفعال.
- برچسب‌گذاری قابلیت‌ها:
  - `implemented-untested`: در کد موجود است ولی تست خودکار/شواهد کافی ندارد.
  - `implemented-partially-tested`: بخشی از معیارهای این قابلیت تست شده، اما پوشش route/شاخه/حالت‌های منفی آن کامل نیست.
  - `implemented-tested`: معیارهای پذیرش متصل به تست سبز و نگهداری‌شده هستند.
  - `mysql-concurrency`: علاوه بر تست عادی، MySQL لازم است.
  - `staging-only`: فقط سناریوی واقعی sandbox/staging.
  - `external-blocked`: پیاده‌سازی موجود است اما اعتبارنامه/زیرساخت بیرونی برای آزمون واقعی لازم است.
  - `implementation-gap`: رفتار هنوز در کد وجود ندارد؛ تست نباید جایگزین پیاده‌سازی یا مدرک تکمیل تلقی شود.
  - `out-of-scope`: فقط با توجیه ثبت‌شده.
  - `assessed-overview`: فقط برای ردیف والد بخش roadmap؛ ادعاهای مرور معماری به ردیف‌های requirement تفکیک شده‌اند، اما این برچسب به‌تنهایی پیاده‌سازی یا پوشش تست را تأیید نمی‌کند.
- ثبت وضعیت‌های فعلی بدون پاک‌کردن شواهد تست دستی قدیمی؛ شواهد دستی و خودکار جدا نگه داشته شوند.
  - ثبت دقیق روش اجرای هر تست موجود و شاهد فعلی، بدون تعمیم یک تست محدود به کل feature.

### پوشش الزامی

- Disable: الزام کد معتبر، پاک‌سازی کامل secret/pending/recovery state و رویداد امنیتی.
- ورود وب و موبایل: بدون توکن/session قبل از عامل دوم؛ challenge timeout، یک‌بارمصرف، حد تلاش، کاربر غیرفعال، 2FA خاموش و TOTP/recovery معتبر.

Pint، `composer validate --no-check-publish` و `git diff --check` موفق بودند. اجرای scheduler در production و cache/lock چندمیزبانه همچنان تا زمان استقرار موکول است.

## موارد خارج از تکمیل خودکار تا فراهم‌شدن پیش‌نیاز

- آزمون تحویل واقعی Expo/EAS و SMS production نیازمند credential و زیرساخت مجزاست؛ بخش provider/job موجود همچنان باید با fake پوشش داده شود.
- Firebase App Check/reCAPTCHA، adapterهای Sadad/SEP، backup/restore و مانیتورینگ/alerting تا زمان پیاده‌سازی در کد `implementation-gap` هستند؛ تست فرضی برای آن‌ها به‌معنی تکمیل نیست.
- استقرار و بازیابی production نیازمند محیط عملیاتی مجزا و خارج از suite PHPUnit است.
- هر رفتار محصولی که هنوز در کد وجود ندارد؛ ابتدا باید تصمیم/پیاده‌سازی آن جداگانه تأیید شود و سپس به ماتریس تست افزوده گردد.
**به‌روزرسانی snapshot پس از ارزیابی بخش ۲۴:** بخش‌های ۱ تا ۲۴ اکنون ۲۱۵ requirement دارند (بخش ۲۴: ۵ requirement)؛ ماتریس ۵۸۳ ردیف دارد: ۲۱۰ فایل، ۹۷ route، ۲۵ بخش roadmap، ۲۱۵ requirement، ۲۷ gap و ۹ exclusion دایرکتوری. مسیرهای API و وب نشان می‌دهند 2FA با TOTP، secret رمزگذاری‌شده، recovery code هش‌شده و یک‌بارمصرف، challenge پنج‌دقیقه‌ای و سقف پنج تلاش پیاده‌سازی شده؛ ورود API تا تأیید عامل دوم token نمی‌دهد و ورود مدیر تا آن زمان نشست احراز‌شده نمی‌سازد. این ارزیابی ایستا بود و tests اجرا نشدند. Firebase App Check در client/backend و reCAPTCHA v3 در جریان وب یافت نشد؛ gap موجود `firebase-app-check` با شواهد client/server و استثناهای callback/webhook به‌روزرسانی شد. User activity log فقط name/profile-photo را ثبت می‌کند و password/2FA secrets در آن نیستند، اما Transaction و PaymentOrder برای audit، amount/balance snapshot را ثبت می‌کنند؛ این را با الزام بخش ۷ برای حفظ audit مالی تطبیق دهید و scope حساسیت `balance_after` را با مالک محصول روشن کنید. API فعلی Sanctum bearer-token و غیر-stateful است؛ middleware برای X-Requested-With پیدا نشد، درحالی‌که admin web در گروه web از CSRF session استفاده می‌کند. این مورد به‌عنوان شکاف قرارداد roadmap ثبت شد، نه آسیب‌پذیری CSRF اثبات‌شده؛ معماری cookie-auth لازم است پیش از فعال‌کردن ادعای SPA روشن شود. محدودیت نرخ روی OTP، 2FA و برخی عملیات مالی/admin هست، اما لغو اشتراک، تغییرات پروفایل/حریم خصوصی، logout-all، لغو دستگاه و بعضی تغییرات push/media throttle صریح ندارند؛ gap `sensitive-api-rate-limits` افزوده شد. Retry-After از روی اجرای واقعی بررسی نشد. هیچ تست، Firebase/EAS، دیتابیس، سرویس یا deploy اجرا نشد؛ log پیوست‌شده صفر خط است. فاز صفر باز می‌ماند و بخش ۲۵ و تطبیق نهایی فایل/route/test باقی‌اند.
**به‌روزرسانی snapshot نهایی پس از ارزیابی بخش ۲۵:** چک‌لیست roadmap شامل ۳۷ نشانگر است (۱۰ complete، ۵ partial، ۲۲ pending در متن فعلی). این بخش گردآورندهٔ معیارهای بخش‌های ۱ تا ۲۴ است، نه ۳۷ الزام رفتاری تازه؛ بنابراین requirement و gap تکراری ساخته نشد و ردیف section 25 به `assessed-overview` تغییر کرد. چند نشانگر پرداخت در roadmap هنوز unchecked هستند، درحالی‌که رکوردهای بخش‌های ۹/۱۰ در ماتریس پیاده‌سازی مربوط را موجود ولی `implemented-untested` ارزیابی کرده‌اند؛ وضعیت checklist باید با شواهد هماهنگ شود، بدون اینکه پیاده‌سازی موجود معادل پوشش آزمون تلقی شود. مواردی مانند تهیهٔ ابزار/حساب، شاخه‌های GitHub، مقادیر `.env` واقعی، اجرای migration، پیکربندی production، صحت اجرای تست‌های تاریخی و استقرار با این بررسی مخزن قابل اثبات نیستند. ماتریس فعلی ۵۸۳ ردیف دارد: ۲۱۰ فایل، ۹۷ route، ۲۵ بخش roadmap، ۲۱۵ requirement، ۲۷ gap و ۹ exclusion دایرکتوری؛ این شمارش به‌تنهایی اثبات‌کنندهٔ تطبیق کامل تمام فایل‌ها/routeها با تست موفق نیست. هیچ تست، build، migration، دیتابیس، credential، سرویس خارجی یا deploy اجرا/بررسی نشد؛ فایل `storage/logs/laravel.log` پیوست‌شده صفر بایت است. فاز صفر ارزیابی نقشهٔ راه به بخش ۲۵ رسید، اما closure معیارهای تست، route/actor، تست‌های مالی و امنیتی، MySQL concurrency، حدنصاب coverage و K6 staging همچنان برقرار نیست و باید در فازهای مجاز بعدی انجام شود.
**به‌روزرسانی پس از پیاده‌سازی محدودیت نرخ API:** برای کل گروه کاربرِ احراز‌شده در `routes/api.php`، middleware نام‌دار `throttle:sensitive-api` اضافه شد. limiter در `AppServiceProvider` سقف تجمیعی ۱۲۰ درخواست در دقیقه برای هر کاربر و IP دارد؛ سقف هر route برای GET/HEAD/OPTIONS برابر ۶۰ در دقیقه برای کاربر و ۱۲۰ برای IP، و برای سایر متدها ۱۰ برای کاربر و ۳۰ برای IP است. limiter پس از احراز هویت و بررسی فعال‌بودن حساب، اما پیش از ثبت فعالیت کاربر اجرا می‌شود. محدودیت‌های موجود OTP/2FA و admin API دست‌نخورده‌اند؛ callback و webhook پرداخت همچنان بیرون از گروه کاربر و با throttle جداگانهٔ فعلی هستند. requirement مربوط در ماتریس به `implemented-untested` تغییر کرد و gap پیاده‌سازی آن حذف شد؛ ماتریس اکنون ۵۸۲ ردیف، ۲۱۵ requirement و ۲۶ gap دارد. هیچ تستی مطابق خواستهٔ کاربر اجرا یا تغییر داده نشد؛ پاسخ 429/Retry-After، trusted proxy، cache در production و مناسب‌بودن آستانه‌ها برای ترافیک واقعی هنوز نیازمند اعتبارسنجی مجاز هستند.
**بررسی پیکربندی cache و IP limiter:** در `config/cache.php` default برابر `database` است و `.env.example` نیز `CACHE_STORE=database` دارد؛ migration جدول‌های `cache` و `cache_locks` را می‌سازد. بنابراین limiter میان چند instance فقط وقتی هماهنگ است که همگی به database/cache backend مشترک و prefix یکسان وصل باشند؛ نمونهٔ env از SQLite محلی استفاده می‌کند و آمادگی production را اثبات نمی‌کند. Redis store هم در config موجود است، ولی فعال‌بودنش تأیید نشده است. Laravel به‌طور پیش‌فرض middleware `TrustProxies` را در global stack دارد؛ در کد برنامه تنظیم trusted proxy و متغیر `TRUSTED_PROXIES` یافت نشد. پس در نصب معمولی، پشت reverse proxy احتمالاً IP اتصال پراکسی مبنا می‌شود مگر محیط میزبان (مثل Laravel Cloud/Forge) خودکار تنظیم کند؛ برای چند کاربر پشت یک proxy این موضوع می‌تواند limiterهای per-IP را تجمیع و باعث 429 زودهنگام کند. IP واقعی را فقط پس از تعیین آدرس/CIDR پراکسی‌های واقعی و اعتماد محدود به همان‌ها تنظیم کنید؛ اعتماد به همهٔ forwarded headers/proxies ناامن است. از نظر مصرف، سقف ۱۰ درخواست تغییردهنده در دقیقه برای هر کاربر/route و ۶۰ درخواست خواندنی در دقیقه برای کاربر، به‌علاوه سقف‌های IP/تجمیعی، برای استفادهٔ معمول غیرتهاجمی به‌نظر می‌رسند؛ اما چند دستگاه و retryهای کلاینت و کاربران پشت NAT می‌توانند روی سقف‌های تجمیعی اثر بگذارند و telemetry واقعی در دسترس نیست، پس فعلاً مقدارها تغییر نکردند. هیچ `.env` واقعی، connection، تست یا درخواست شبکه‌ای بررسی/اجرا نشد.
**آماده‌سازی برای معماری انتخاب‌شده (یک VPS پشت Nginx با Redis):** `config/trustedproxy.php` و bootstrap به کد اضافه شدند تا `TRUSTED_PROXIES` فقط از allowlist صریح IP/CIDR خوانده شود؛ در صورت unset بودن هیچ proxy دلخواهی trusted نمی‌شود و فقط هدرهای X-Forwarded-For/Proto/Port پذیرفته می‌شوند. `.env.example` همچنان برای توسعهٔ محلی روی database cache باقی مانده و مقدارهای production را صرفاً به‌صورت comment راهنما آورده است؛ فایل `.env` واقعی یا تنظیم Nginx/Redis میزبان تغییر نکرده است. برای استقرار باید Redis و افزونهٔ PHP client واقعاً آماده شوند، `CACHE_STORE=redis` در secret environment تنظیم شود و `TRUSTED_PROXIES` دقیقاً با آدرس upstreamی که Nginx از آن به PHP-FPM وصل می‌شود منطبق گردد. Nginx باید forwarded headers را خودش بازنویسی کند؛ آدرس proxy، هدرهای واقعی، کارکرد Redis و دریافت 429/Retry-After در staging هنوز تأیید نشده‌اند. ماتریس پس از افزودن رکورد فایل `config/trustedproxy.php` به ۵۸۳ ردیف رسیده است: ۲۱۱ فایل، ۹۷ route، ۲۵ بخش، ۲۱۵ requirement، ۲۶ gap و ۹ exclusion. PHP lint و بررسی ساختار CSV/whitespace انجام می‌شوند؛ هیچ تست، `.env` واقعی، دیتابیس یا سرویس خارجی اجرا/خوانده نمی‌شود.
**رسیدگی به پاسخ 429 در اپ:** formatter خطای API در `bootstrap/app.php` اکنون `Retry-After` و headerهای `X-RateLimit-*` را هنگام ساخت Problem Details حفظ می‌کند. helper موبایل در `auth-api.ts` مقدار ثانیه‌ای یا HTTP-date را می‌خواند، آن را در `AuthApiError.retryAfterSeconds` نگه می‌دارد و پیام فارسی همراه زمان انتظار می‌سازد. `PlanAccessProvider` retry خودکار immediate را برای 429 متوقف می‌کند و از retry-on-mount، refetch-on-reconnect و refetch-on-focus پس از خطای 429 جلوگیری می‌کند؛ درخواست‌های دستی/دوباره‌زنی در سایر خطاها طبق رفتار موجود باقی‌اند. هیچ تستی اجرا یا تغییر داده نشد؛ header preservation و رفتار React Query باید در اعتبارسنجی مجاز بعدی پوشش داده شوند. ماتریس ۵۸۳ ردیف، ۲۱۱ فایل، ۲۱۵ requirement و ۲۶ gap دارد.
