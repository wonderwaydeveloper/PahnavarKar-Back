# اجرای Scheduler و Queue Worker روی Ubuntu در ArvanCloud

این راهنما و فایل‌های `deploy/ubuntu/*.example` الگوی آغازین برای یک سرور Ubuntu هستند؛ هیچ سرور ArvanCloud ایجاد یا تغییر داده نشده است. پیش از نصب، مسیر برنامه و کاربر سرویس را با چیدمان واقعی سرور جایگزین کنید. از اجرای Laravel با `root` خودداری کنید.

## استقرار کنترل‌شدهٔ Staging

فایل `.github/workflows/deploy-staging.yml` یک مسیر دستی برای استقرار Backend در Staging فراهم می‌کند. workflow فقط با اجرای دستی از صفحهٔ GitHub Actions شروع می‌شود، ابتدا تست‌های PHPUnit و build فرانت‌اند را اجرا می‌کند و در صورت موفقیت، یک release مستقل را با Ansible روی Ubuntu منتشر می‌کند. این workflow هرگز Production را هدف نمی‌گیرد و به‌تنهایی سرور، firewall، DNS، TLS یا دیتابیس مدیریت‌شده ایجاد/پیکربندی نمی‌کند.

### پیش‌نیازهای زیرساخت Staging

1. Ubuntu باید از قبل با PHP CLI/FPM سازگار با PHP 8.3، افزونه‌های موردنیاز برنامه (از جمله PDO MySQL و ZIP)، Nginx، Supervisor و Cron آماده شده باشد. workflow، Composer و Node را روی runner اجرا می‌کند؛ برای این مسیر به نصب آن‌ها روی سرور نیازی نیست. یک کاربر SSH اختصاصی بسازید که عضو گروه `www-data` باشد، مالک `<STAGING_APP_ROOT>` باشد و دسترسی دیگری به سیستم نداشته باشد. این playbook عمداً privilege escalation یا `sudo` اجرا نمی‌کند.
2. پیش از اولین deploy، `<STAGING_APP_ROOT>` را با مالکیت کاربر deploy و گروه `www-data` و مجوز `0750` ایجاد کنید. `root` در Nginx باید به `<STAGING_APP_ROOT>/current/public` و Supervisor/Cron به `<STAGING_APP_ROOT>/current` اشاره کنند. قالب‌های `deploy/ubuntu/pahnavarkar-worker.conf.example` و `deploy/ubuntu/pahnavarkar-scheduler.cron.example` را متناسب با مسیر واقعی نصب کنید.
3. دیتابیس Staging را در سرویس مدیریت‌شده بسازید؛ اتصال MySQL از سرور Ubuntu مجاز باشد و TLS/CA مطابق مستندات همان ارائه‌دهنده تنظیم شود. از کاربر و credential جدا از Production با حداقل مجوز لازم استفاده کنید.
4. یک میزبان HTTPS برای Staging آماده کنید که مسیر Laravel `/up` را از اینترنت runnerهای GitHub پاسخ دهد. کلید SSH و fingerprint میزبان را از مسیر مورداعتماد تهیه و fingerprint را پیش از ثبت تأیید کنید؛ به `ssh-keyscan` هنگام deploy برای اعتماد اولیه تکیه نکنید.
5. شاخه و commit موردنظر را بازبینی کنید. workflow به‌صورت دستی از commit انتخاب‌شده اجرا می‌شود؛ برای Environment با نام `staging` در تنظیمات GitHub محدودیت دسترسی مناسب بگذارید. هیچ secret یا دسترسی Production را به این Environment ندهید.

### تنظیم GitHub Environment

در تنظیمات مخزن، Environment با نام دقیق `staging` بسازید و این مقادیر را تعریف کنید:

| نوع | نام | مقدار |
|---|---|---|
| Variable | `STAGING_HOST` | IP نسخهٔ ۴ یا نام DNS سرور Ubuntu |
| Variable | `STAGING_USER` | کاربر SSH اختصاصی با نام سادهٔ Linux؛ مالک app root و عضو گروه `www-data`، بدون نیاز به sudo |
| Variable | `STAGING_APP_ROOT` | مسیر مطلق زیر `/var/www/`، مانند `/var/www/pahnavarkar` |
| Variable | `STAGING_HEALTHCHECK_URL` | نشانی HTTPS به `/up`، مانند `https://staging.example.com/up` |
| Secret | `STAGING_SSH_PRIVATE_KEY` | کلید خصوصی اختصاصی Staging، بدون استفادهٔ مجدد از کلید Production |
| Secret | `STAGING_SSH_KNOWN_HOSTS` | خط(های) `known_hosts` با fingerprint تأییدشده برای همان میزبان |
| Secret | `STAGING_ENV_FILE` | محتوای کامل `.env` اختصاصی Staging |

`STAGING_ENV_FILE` باید `APP_ENV=staging`، `APP_DEBUG=false`، `APP_KEY` و `APP_URL` با HTTPS و نیز `DB_CONNECTION=mysql` و تنظیمات اتصال MySQL مدیریت‌شده (`DB_HOST`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`) را داشته باشد. برای limiterها `CACHE_STORE` را روی یک store اتمی و مشترک مانند `database` یا `redis` تنظیم کنید؛ اگر `cache.limiter` جداگانه تنظیم شده، همان store مؤثر است. همهٔ instanceهای برنامه و worker باید backend، جدول/اتصال یا Redis DB و `CACHE_PREFIX` یکسان داشته باشند. storeهای `array`، `null` و `failover` برای limiter در محیط staging/production پذیرفته نمی‌شوند؛ از failover به store محلی نیز استفاده نکنید، چون پس از اختلال backend شمارنده‌ها بین instanceها جدا می‌شوند.

اگر برنامه پشت Nginx یا load balancer است، `TRUSTED_PROXIES` را فقط با IP/CIDR واقعی peerای که اتصال را به PHP-FPM می‌رساند تنظیم کنید؛ مقدار نمونهٔ `.env.example` را بدون تطبیق با سرور کپی نکنید. اگر این متغیر خالی بماند، Laravel از `REMOTE_ADDR` استفاده می‌کند و ممکن است همهٔ کاربران پشت یک proxy در bucket یک IP جمع شوند. proxy باید هدرهای client-supplied را قابل‌اعتماد فرض نکند و `X-Forwarded-For` را از آدرس client که خودش احراز کرده بازنویسی/بسازد؛ استفادهٔ کور از زنجیرهٔ ورودی یا `X-Forwarded-For` ارسالی کاربر می‌تواند جعل IP را ممکن کند. اگر CDN یا load balancer دیگری جلوی Nginx قرار دارد، زنجیرهٔ آدرس‌ها و real-IP configuration را فقط با محدوده‌های رسمی و تأییدشدهٔ همان upstream تنظیم کنید. دسترسی مستقیم عمومی به PHP-FPM یا مسیر اپلیکیشن که proxy مورداعتماد را دور می‌زند ببندید؛ فقط Nginx/upstreamهای تعیین‌شده باید به backend دسترسی داشته باشند.

پس از تنظیم staging، با یک درخواست از مسیر proxy و یک درخواست مستقیم/با forwarded header جعلی بررسی کنید که IP واقعی فقط در حالت proxy تأییدشده استخراج می‌شود و limiter برای IPهای متفاوت bucket جدا می‌سازد. آزمون‌های Feature رفتار middleware و limiter را پوشش می‌دهند، اما IP upstream، بازنویسی واقعی هدرها، firewall و مسیر شبکهٔ staging/production را اثبات نمی‌کنند. مقادیر واقعی را فقط در Environment secret نگه دارید؛ آن‌ها را در مخزن، artifact یا log قرار ندهید. تنظیمات باید شامل سایر سرویس‌های موردنیاز همین محیط نیز باشد. SMS، پرداخت، ایمیل و ذخیره‌سازی خارجی را با credentialهای جداگانهٔ staging و مقصدهای آزمایشی فعال کنید؛ workflow آن‌ها را خودکار فعال نمی‌کند.

### اجرای استقرار

از **Actions → Deploy staging → Run workflow**، commit بازبینی‌شده را انتخاب کنید. پس از تست/build، workflow artifact را بدون `.env` و runtime storage می‌سازد، به سرور متصل می‌شود، `.env` را فقط در release جدید قرار می‌دهد، storage را بین releaseها مشترک می‌کند، `php artisan migrate --force` و `config:cache` را اجرا می‌کند، symlink فعال را به‌صورت اتمیک تغییر می‌دهد، worker را graceful بازنشانی می‌کند و پاسخ 200 از `/up` را بررسی می‌کند. تنظیم Sentry از callable مبتنی بر نام کلاس استفاده می‌کند تا با config cache سازگار باشد. در موفقیت، پنج release جدید و release قبلی برای rollback نگه‌داری می‌شوند؛ فایل `.env` نسخه‌های نگه‌داری‌شده نیز روی سرور باقی می‌ماند، پس دسترسی سیستم‌عامل به app root را محدود کنید و هنگام چرخش secretها اثر نسخهٔ قبلی را در نظر بگیرید.

اگر فعال‌سازی یا health check شکست بخورد، workflow تلاش می‌کند symlink برنامه را به release قبلی برگرداند و workerها را بازنشانی کند. migration دیتابیس به‌طور خودکار rollback نمی‌شود؛ migrationها را برای سازگاری با release قبلی طراحی و روی دادهٔ آزمایشی بررسی کنید. `/up` فقط بالا آمدن HTTP/Laravel را بررسی می‌کند و سلامت کامل دیتابیس، صف، پیامک، پرداخت یا بکاپ را اثبات نمی‌کند.

این مسیر فقط deploy کد به Staging را خودکار می‌کند. ساخت/سخت‌سازی ماشین، firewall، TLS، دیتابیس مدیریت‌شده، دسترسی‌های provider، پایش و اثبات restore بکاپ همچنان جداگانه باید آماده و تأیید شوند. هیچ workflow یا secret مربوط به Production در این فاز اضافه نشده است.

### انتخاب سرویس پیامک

برای کاوه‌نگار، `KAVENEGAR_ENABLED=true`، کلید `KAVENEGAR_API_KEY` و در صورت نیاز `KAVENEGAR_SENDER` را فقط در secretهای محیط سرور تنظیم کنید. secret را از فرم پنل ادمین یا تنظیمات دیتابیس وارد نکنید. ملی‌پیامک نیز با secretهای `MELIPAYAMAK_*` پیکربندی می‌شود. برای فعال‌شدن آزمون ارسال از پنل، یک قالب تأییدشدهٔ جداگانه و بدون متغیر با متن «پیام آزمایشی سرویس پیامک پهناورکار؛ نیازی به پاسخ نیست.» در پنل ملی‌پیامک بسازید و شناسهٔ آن را به‌عنوان `MELIPAYAMAK_TEST_BODY_ID` در secret محیط قرار دهید؛ قالب OTP را برای آزمون به‌کار نبرید. پس از deploy نسخه‌ای که مجوز `manage sms providers` را اضافه می‌کند، یک‌بار `php artisan db:seed --class=RolePermissionSeeder --force` را اجرا کنید تا مجوز برای نقش‌های Admin/Owner ثبت شود؛ سپس از **تنظیمات سامانه ← سرویس پیامک** بین providerهای آماده سوییچ کنید. تنظیم انتخاب‌شده در تنظیمات runtime دیتابیس ثبت می‌شود، اما credentialها در آن ذخیره نمی‌شوند.

در همان صفحه امکان ارسال پیام ثابت آزمایشی به شمارهٔ موبایل ایران فراهم است. محدودیت endpoint برای هر ادمین و هر شماره یک ارسال در دقیقه و پنج ارسال در ساعت است. پاسخ موفق provider فقط پذیرش درخواست را نشان می‌دهد، نه تحویل قطعی به گوشی؛ تحویل را روی دستگاه مقصد بررسی کنید. اگر log provider محلی فعال باشد، آزمون صرفاً ثبت محلی می‌کند و SMS واقعی نمی‌فرستد.

پیش از فعال‌کردن صف، provider انتخاب‌شده باید روی همان محیط با شمارهٔ آزمایشی و اعتبارنامهٔ محدود بررسی شود؛ صف همچنان تا آماده‌بودن Queue پایدار و Worker تحت نظارت خاموش بماند. هر تغییر `.env` نیازمند refresh کردن config cache و راه‌اندازی مجدد worker است.

## تنظیم Queue Worker

صف فعلی برنامه از اتصال `database` استفاده می‌کند. OTP در صف `sms` و تحویل اعلان‌های صندوق و Push در صف پیش‌فرض (`default`) قرار می‌گیرند؛ قالب Worker صف‌های `default,sms` را به همین ترتیب پردازش می‌کند تا اطلاعیه‌های کاربران پشت صف پیامک‌ها معطل نمانند. تنظیمات jobها حداکثر سه تلاش دارند و `retry_after` صف دیتابیس ۹۰ ثانیه است. قالب Supervisor مقدار timeout را ۶۰ ثانیه می‌گذارد تا از `retry_after` کوتاه‌تر باشد.

برای OTP، هر Job سه تلاش با timeout حداکثر ۲۰ ثانیه و backoffهای ۱۰ و ۳۰ ثانیه دارد؛ `retry_after=90` باید از timeout Job بزرگ‌تر بماند. زمان مدل‌شدهٔ اجرای سه تلاش و backoffها ۱۰۰ ثانیه است، اما این عدد تأخیر انتظار در صف را شامل نمی‌شود. Job پیش از هر ارسال اعتبار پنج‌دقیقه‌ای را دوباره بررسی می‌کند؛ اگر صف آن‌قدر عقب بماند که کد منقضی شود، پیام عمداً ارسال نمی‌شود و Job با موفقیت کنار گذاشته می‌شود، نه این‌که در `failed_jobs` ثبت شود. برای همین فقط running بودن Supervisor کافی نیست: سن/قدیمی‌ترین Job صف `sms` را با حاشیهٔ امن بسیار کمتر از TTL پایش کنید و برای backlog، توقف worker، رشد `failed_jobs` و شکست نهایی Sentry هشدار عملیاتی تعریف و در staging تحویل هشدار را آزمایش کنید.

تلاش مجدد در خطای شبکه تضمین exactly-once نمی‌دهد: ممکن است provider پیام را پذیرفته باشد ولی پاسخ آن به برنامه نرسد؛ retry همان OTP ممکن است SMS تکراری بفرستد، و مسیر هم‌زمان در بعضی timeoutهای مبهم ممکن است به کاربر 503 بدهد در حالی که پیام دیرتر برسد. پیش از اتکا، نرخ تحویل و پاسخ واقعی provider را روی شمارهٔ آزمایشیِ مجاز بررسی کنید، duplicate/timeout و درخواست کد تازه را ثبت و مشاهده کنید و رفتارهای مبهم را با قرارداد provider تطبیق دهید. موفقیت پاسخ provider فقط پذیرش درخواست است، نه تحویل به handset.

1. در سرور Ubuntu، PHP و extensionهای موردنیاز برنامه، Cron و Supervisor را نصب و نسخه‌ها را با `composer.json` و مستندات Laravel تطبیق دهید. Composer فقط برای استقرار دستی/ساخت روی سرور لازم است؛ workflow استقرار Staging آن را روی runner اجرا می‌کند.
2. مسیر ثابت برنامه در قالب Supervisor و Cron را به مسیر واقعی استقرار تغییر دهید. نمونه از `/var/www/pahnavarkar/current` استفاده می‌کند؛ اگر از symlink برای releaseها استفاده می‌کنید، این مسیر باید پس از هر استقرار همچنان به release فعال اشاره کند.
3. کاربر اجرای Worker و Cron باید غیرریشه‌ای باشد و به کد، `.env` و `storage` دسترسی لازم داشته باشد. در مسیر Staging این workflow، آن‌ها می‌توانند با `www-data` اجرا شوند؛ کاربر deploy عضو گروه `www-data` است و دسترسی فایل‌ها بر همین اساس تنظیم می‌شود. اگر کاربر سرویس را عوض می‌کنید، گروه و مجوزهای مشترک را نیز هماهنگ کنید. دسترسی نوشتن را فقط به مسیرهای موردنیاز مثل `storage` و `bootstrap/cache` بدهید؛ از مجوزهای عمومی مانند `777` استفاده نکنید.
4. پس از تأیید `.env` امن و آماده‌سازی پایگاه‌داده و queue tables، کپی قالب Supervisor به `/etc/supervisor/conf.d/pahnavarkar-worker.conf` را انجام دهید و سپس `supervisorctl reread`, `supervisorctl update` و `supervisorctl status pahnavarkar-worker:*` را بررسی کنید.
5. هر بار که کد یا تنظیمات worker تغییر می‌کند، worker را با `php artisan queue:restart` به‌صورت graceful بازنشانی کنید و بررسی کنید Supervisor پردازه را دوباره بالا آورده باشد. `autorestart` جایگزین بررسی سلامت صف یا هشداردهی نیست.
6. پیش از فعال‌سازی `SMS_OTP_QUEUE_ENABLED=true`، `.env` و config cache را بازبینی کنید: provider انتخاب‌شده باید credential و قالب OTP معتبر داشته باشد، queue driver و جدول/دسترسی لازم آماده باشد، و worker همان connection و نام صف `sms` را پردازش کند. با SMS ثابتِ تستیِ پنل و سپس یک OTP کنترل‌شده به شمارهٔ متعلق به آزمونگر مجاز، پذیرش provider و دریافت handset را جداگانه بررسی کنید؛ کد OTP را در log/گزارش آزمون ثبت نکنید.
7. ابتدا staging و با مقصدهای آزمایشی اجرا کنید. پیکربندی provider، worker، queue lag، خطای نهایی و دریافت هشدار Sentry را تأیید کنید؛ tests مبتنی بر `Http::fake` فقط قرارداد درخواست/پاسخ را می‌سنجند و credential، تحویل مخابراتی یا سلامت provider واقعی را اثبات نمی‌کنند. در صورت ابهام provider یا نبود مقصد مجاز، صف OTP را خاموش نگه دارید.

قالب Worker عمداً یک پردازه دارد تا نقطهٔ شروع محافظه‌کارانه باشد؛ ظرفیت واقعی را با مشاهدهٔ CPU، حافظه و عقب‌ماندگی صف تعیین کنید. چند worker یا سرور برنامه را بدون اندازه‌گیری و تصمیم دربارهٔ صف، cache و lockهای مشترک اضافه نکنید.

محدودیت نرخ و lockهای OTP از cache مؤثر Laravel استفاده می‌کنند (`cache.limiter` در صورت تنظیم، وگرنه `cache.default`). برنامه در محیط‌های غیرمحلی/غیرآزمایشی storeهای غیراتمی یا محلی و failover را برای limiter رد می‌کند؛ بااین‌حال این guard اشتراک واقعی backend، یکسان‌بودن prefix/اتصال، یا سلامت cache در سرور را اثبات نمی‌کند. middleware پراکسی global پیش از limiter اجرا می‌شود و فقط IPهای `TRUSTED_PROXIES` مجازند `X-Forwarded-For`، `X-Forwarded-Proto` و `X-Forwarded-Port` را تعیین کنند؛ `X-Forwarded-Host` trusted نیست. پیش از اتکا، cache و تنظیمات proxy را روی همهٔ instanceها تأیید و رفتار اختلال cache/جعل هدر را در محیط آزمایشی بررسی کنید.

## فعال‌کردن Scheduler

Cron باید هر دقیقه `php artisan schedule:run` را اجرا کند. مسیر Cron باید مطلق و پایدار باشد و کاربر آن بتواند در `storage/logs` بنویسد. در فایل نمونه، خروجی scheduler در همان مسیر ثبت می‌شود؛ برای فایل log نیز rotation و محدودیت دسترسی مناسب در نظر بگیرید.

پس از نصب نمونه در `/etc/cron.d/pahnavarkar-scheduler`، وضعیت سرویس Cron را بررسی و با `php artisan schedule:list` ثبت کارها را مشاهده کنید. این فرمان فهرست را نشان می‌دهد و task پاک‌سازی `failed_jobs` را اجرا نمی‌کند. رویدادهای برنامه از جمله pruning روزانهٔ jobهای ناموفق پس از ۷۲۰ ساعت و حذف OTPها یک روز پس از انقضا فقط زمانی رخ می‌دهند که Cron فعال باشد.

پاک‌سازی OTP هر روز ساعت ۰۳:۲۰ UTC اجرا می‌شود و رکوردهای مصرف‌شده یا مصرف‌نشده‌ای را که حداقل یک روز از `expires_at` آن‌ها گذشته باشد، batchشده حذف می‌کند. این رکوردها فقط hash کد دارند اما شماره تلفن را نگه می‌دارند؛ این cleanup جایگزین backup-retention، سیاست نگهداری activity log یا تعهدات حقوقی نگهداری سوابق نیست. در صورت نیاز حسابرسی خاص، مدت را پیش از استقرار با سیاست مصوب تطبیق دهید.

برای چند میزبان Scheduler، قفل‌های `withoutOverlapping` باید از cache مشترک استفاده کنند. تا پیش از انتخاب و راه‌اندازی cache مشترک، فقط یک میزبان Scheduler را فعال نگه دارید.

## راه‌اندازی Sentry

اتصال Laravel، گزارش گزینشی خطاها و پالایش اطلاعات صف در کد پیاده‌سازی شده‌اند؛ تست‌های خودکار از transport ضبط‌کننده استفاده می‌کنند و به Sentry واقعی چیزی ارسال نمی‌کنند. پیش از اتکا به پایش Production:

1. پروژهٔ Sentry و مالک دریافت هشدار را برای محیط‌های موردنیاز تعیین کنید. دسترسی پروژه و مدت نگهداری رخدادها را متناسب با سیاست حریم خصوصی سازمان محدود/بازبینی کنید.
2. DSN را فقط در secret store همان محیط، در `SENTRY_LARAVEL_DSN` قرار دهید؛ آن را در مخزن یا log نگذارید. `SENTRY_ENVIRONMENT` را برای staging/production صریح تنظیم کنید و `SENTRY_RELEASE` را در صورت داشتن شناسهٔ انتشار پایدار، با نسخهٔ مستقر هماهنگ کنید. `SENTRY_SEND_DEFAULT_PII` را `false` نگه دارید مگر تغییر آن پس از بررسی حریم خصوصی و تأیید مسئول مجاز شده باشد.
3. در staging یک خطای کنترل‌شده از مسیر داخلی و غیرقابل‌دسترسی عمومی ایجاد کنید و دریافت رخداد در پروژهٔ درست، environment و release مورد انتظار را بررسی کنید. رخداد آزمایشی را پس از آزمون پاک کنید؛ برای این کار route عمومی یا کلید/اطلاعات واقعی کاربر نسازید.
4. قواعد هشدار و گیرندگان را در Sentry تنظیم کنید؛ با ایجاد یک رخداد آزمون، تحویل هشدار به مسئول را عملاً تأیید کنید. ثبت رخداد بدون قاعدهٔ هشدار و گیرنده، اطلاع‌رسانی عملیاتی نیست.
5. نمونهٔ رخداد را از نظر داده‌های ارسالی و دسترسی‌ها بازبینی کنید. کد، خطاهای HTTP 4xx و statusهای تأییدنشده را فیلتر می‌کند؛ خطاهای HTTP 500/503 و خطاهای بدون status HTTP گزارش می‌شوند. تلاش‌های retry صف ارسال نمی‌شوند؛ شکست نهایی صف با محتوای خطا و request/user/extra پاک‌سازی‌شده گزارش می‌شود.

تست‌های PHPUnit با transport آزمایشی، رفتار فیلتر و پالایش را بررسی می‌کنند؛ موفقیت آن‌ها دسترسی شبکه، DSN، دریافت رخداد یا تحویل هشدار در محیط واقعی را اثبات نمی‌کند. راه‌اندازی Sentry به migration دیتابیس نیاز ندارد و جایگزین پایش uptime، منابع سرور یا بررسی سلامت بکاپ نیست.

## بکاپ و بازیابی

برنامه هر روز ساعت ۰۲:۰۰ UTC، دیتابیس فعال و فایل‌های پروژه/آپلودهای عمومی را در یک آرشیو ZIP رمزگذاری‌شده می‌گذارد و به دیسک خصوصی `backup-s3` می‌فرستد. پاک‌سازی روزانه ساعت ۰۲:۳۰ UTC نسخه‌های قدیمی‌تر از ۳۰ روز را حذف می‌کند؛ بررسی سلامت ساعت ۰۳:۰۰ UTC انجام می‌شود و اگر بکاپ بیش از دو روز قدیمی باشد، وضعیت نامعتبر گزارش می‌شود. `.env`، `vendor`، `node_modules`، فایل‌های log و cache/runtime در آرشیو قرار نمی‌گیرند.

### چک‌لیست زمان راه‌اندازی Production

این موارد را هنگام استقرار Production و پیش از اعلام عملیاتی‌بودن بکاپ، با مسئول اجرا بررسی و نتیجه را ثبت کنید. تا وقتی اجرای بکاپ و بازیابی staging موفق نشده‌اند، وجود کد و زمان‌بندی را معادل آمادگی بکاپ ندانید.

1. PHP باید افزونهٔ ZIP با پشتیبانی AES-256 و ابزار `mysqldump` متناسب با دیتابیس فعال را داشته باشد. فضای موقت سرور باید برای ساخت آرشیو به‌اندازهٔ کافی آزاد باشد.
2. یک bucket خصوصی S3-compatible با دسترسی محدود به عملیات لازم برای نوشتن، فهرست‌کردن و حذف آرشیوها بسازید. credential بکاپ را از credential ذخیره‌سازی فایل‌های کاربر جدا نگه دارید؛ endpoint را برای سرویس‌های غیر AWS تنظیم کنید.
3. متغیرهای `BACKUP_S3_*` را در secret store محیط Production قرار دهید. `BACKUP_ARCHIVE_PASSWORD` باید دست‌کم ۳۲ نویسهٔ تصادفی داشته باشد و نسخه‌ای امن از آن خارج از سرور نگهداری شود؛ بدون آن فرمان زمان‌بندی‌شده بکاپ را اجرا نمی‌کند. گم‌شدن این رمز بازیابی آرشیوها را ناممکن می‌کند.
4. برای هشدار ایمیلی، `BACKUP_NOTIFICATION_EMAIL` و mailer عملیاتی Laravel را تنظیم و دریافت هشدار آزمایشی را تأیید کنید. شکست taskها همچنین با سطح `critical` در log برنامه ثبت می‌شود؛ بدون سامانهٔ دریافت/هشدار log، این ثبت به‌تنهایی اطلاع‌رسانی محسوب نمی‌شود.
5. Cron/Scheduler را برای اجرای `php artisan schedule:run` فعال کنید و `php artisan schedule:list` را بررسی کنید؛ فهرست taskها به‌تنهایی اجرای Scheduler را اثبات نمی‌کند.
6. در پنجرهٔ کنترل‌شده `php artisan backup:run-secure` را اجرا و وجود آرشیو رمزگذاری‌شده روی bucket را با ابزار/کنسول همان provider تأیید کنید.
7. نسخهٔ پشتیبان را در محیط ایزولهٔ staging بازیابی کنید؛ صحت دیتابیس و فایل‌های آپلودی و آزمون‌های سلامت اپ را بررسی و نتیجه، مدت بازیابی و موارد شکست را ثبت کنید. RPO/RTO هدف را با مسئول سرویس تعیین و نتیجه را با آن مقایسه کنید.

پس از راه‌اندازی اولیه، بازیابی به‌صورت خودکار روی Production اجرا نمی‌شود؛ دست‌کم ماهانه یک آرشیو را در staging بازیابی و نتیجه را ثبت کنید. آرشیو شامل `.env` نیست؛ تنظیمات و secretها باید جداگانه از secret store بازیابی شوند. هرگز dump را مستقیماً روی دیتابیس Production برای آزمون بازیابی وارد نکنید.

## مرزهای تأیید

- این قالب‌ها مختص Supervisor و Cron روی Ubuntu هستند، نه پیکربندی اختصاصی API آروان‌کلاد؛ ایجاد firewall، DNS، TLS، دیتابیس مدیریت‌شده یا دسترسی شبکه در آن‌ها انجام نمی‌شود.
- `schedule:list` و وضعیت Supervisor فقط آماده‌بودن ثبت task/پردازه را نشان می‌دهند، نه تحویل پیامک یا Push. آزمون end-to-end باید در staging با credentialهای جداگانه و مقصدهای تأییدشده انجام شود.
- وجود کد و schedule بکاپ به‌معنی اثبات آپلود، هشدار یا بازیابی نیست؛ این‌ها تا تنظیم credentialهای واقعی، اجرای بکاپ و آزمون بازیابی staging تأییدنشده می‌مانند. هیچ migration یا فرمان حذف `failed_jobs` را به‌عنوان آزمون دستی روی production اجرا نکنید.
