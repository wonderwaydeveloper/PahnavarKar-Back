# PahnavarKar Backend

Laravel backend for the PahnavarKar mobile application, Persian-language public website, and Inertia/React admin panel. It provides OTP authentication, subscriptions, wallet and payment workflows, and permission-protected administration.

## Mobile authentication API

The mobile OTP flow uses Laravel Sanctum bearer tokens and Melipayamak SMS:

- `POST /api/v1/auth/otp/send` accepts `phone` and `type` (`login` or `register`). The mobile flow always requests a `login` OTP; the same neutral response is returned for existing and new phone numbers.
- `POST /api/v1/auth/otp/verify` accepts the same phone/type, a six-digit `code`, a UUID `device_id`, and the user's name when required. Existing users receive a session. For a new number, a valid OTP without a name returns `{"status":"profile_required"}`; send the same OTP with a name to complete registration and receive a session.
- Authenticated account management is available through `PATCH /api/v1/auth/profile`, `POST /api/v1/auth/profile/phone` (new phone plus a fresh login OTP), and `DELETE /api/v1/auth/account` (fresh OTP required). The account deletion endpoint also revokes tokens and removes the user's associated records.
- Each authenticated device session stores the operating-system platform, device name, and device model separately, and only one token is retained per device. At most three active device sessions are allowed. Tokens expire after 30 days without an authenticated request; authenticated API activity slides the expiry forward. Expired sessions are pruned hourly by the scheduler and opportunistically during session listing and new logins. A session is labeled stale after seven days without activity but remains revocable before expiration.
- Roles and permissions use Spatie's `web` guard for both web and Sanctum-authenticated users. After applying migrations, run `php artisan db:seed` to create the Owner, Admin, and User roles, baseline permissions, and two unprivileged bootstrap accounts. Existing users without a role, new OTP registrations, and newly created bootstrap accounts receive only the least-privileged User role. `AdminAccountsSeeder` never assigns Owner or Admin and preserves roles assigned explicitly later. Admin web login is available at `/admin/login` and uses OTP for verified phone numbers; only users with the Owner or Admin role can authenticate into the panel. Promote an account only from a trusted server shell after verifying the account ID and phone verification, using `php artisan admin:assign-role 12 Owner` (or `Admin`); the command asks for confirmation. The application never promotes accounts automatically.
- The web app includes a Persian RTL marketing homepage at `/` and an Inertia v3/React admin panel with OTP login and a session-authenticated `/admin` dashboard. The homepage catalog mirrors the mobile app's current `TOOL_DEFINITIONS` and legal categories; subscription durations and prices are rendered from `config/plans.php`. Both are styled with Tailwind CSS, use the locally bundled Shabnam WOFF2 family, share the mobile app's turquoise default palette, and support light, dark, or system color themes saved in the browser; the panel dashboard remains role- and permission-scoped. Admin web pages currently cover the dashboard, users, roles, transactions, withdrawals, discount codes, settings, profile, and two-factor authentication. The API remains a separate interface, primarily for the native mobile client; the planned admin-subdomain deployment should use same-origin Laravel/Inertia web routes rather than browser calls to a separate API host.
- Shabnam WOFF2 files include Persian-digit glyphs. Shabnam redistribution must remain within the project's separately obtained FontNegar license.
- User activity logs record only dirty name/profile-photo changes; phone changes create a marker-only audit in the same transaction as the phone update, never the phone value. Financial model logs use explicit allowlists and exclude idempotency keys, provider references, redirect URLs, and payout/review details. Runtime plan, wallet, site-content, and payment-gateway setting changes are audited with explicit manager attribution and allowlisted fields; provider credentials are never stored or logged through these settings. Subscription lifecycle audit and push listeners are auto-discovered once, avoiding duplicate records or notifications. Role changes are audited explicitly by the Owner-only web user-access action, trusted console command, OTP registration, and default-role seeders; those entries also exclude phone numbers, OTPs, tokens, and other authentication secrets. Activity records older than 365 days are removed daily at 03:00 UTC by Laravel's scheduler. Production must invoke `php artisan schedule:run` every minute; deployments with multiple scheduler hosts need a shared cache store for overlap locks.
- Plan prices and durations are defined in `config/plans.php`. `GET /api/v1/plans` lists the configured premium plans. The product does not offer a trial period. Authenticated users can inspect their current subscription at `GET /api/v1/auth/subscription` and cancel the active subscription at `DELETE /api/v1/auth/subscription`. Cancellation is scheduled for the end of the current period, so access remains active until `ends_at`; it does not refund the purchase. Paid plans are purchased with `POST /api/v1/auth/subscription/purchase` (`plan_key`, optional `discount_code`, and a UUID `Idempotency-Key` header); price is resolved server-side from `config/plans.php`. The purchase automatically uses available wallet balance first and charges the remainder through the configured gateway. Poll `GET /api/v1/auth/payment-orders/{id}` for the final order/subscription state. A payment failure refunds the wallet contribution and releases any reserved discount.
- The internal wallet balance and transaction ledger use integer tomans (`TOMAN`); `GET /api/v1/auth/wallet` returns the balance and `GET /api/v1/auth/wallet/transactions` returns the authenticated user's paginated ledger. Wallet credits are only accepted by the trusted `WalletService` after an external payment has been verified; there is no client credit/deposit endpoint. Purchases debit the wallet atomically through the service and require a UUID idempotency key; one-time internal refunds are available for qualifying failed purchases.
- The withdrawal request and admin-review workflow is implemented but disabled by default. Do not set `WALLET_WITHDRAWALS_ENABLED=true` until an outbound payout provider and a secure verified bank-destination flow are configured. When enabled, users create/list requests at `POST` and `GET /api/v1/auth/wallet/withdrawal-requests`; creation requires `amount` and a client-generated UUID `idempotency_key`, and reserves the amount from the available balance. Admins with `manage wallet` (Owner and Admin by default) can list requests awaiting review or payout at `GET /api/v1/admin/wallet/withdrawal-requests` and approve or reject using the corresponding `/.../{id}/approve` or `/.../{id}/reject` route. Rejection releases the reserved balance as a separate ledger entry; an approved-but-not-paid request can still be rejected and released. Approval means approved and awaiting payout; it does not transfer money. The external payout provider and verified destination-account flow are not configured, so no request can be marked paid or trigger a bank transfer until that integration is added. Limits are 100,000 toman per request and 500,000 toman per day across `pending`, `approved_pending_payout`, and `paid` requests; rejected requests do not count.
- Admins with `view transactions` can browse the paginated, all-user ledger at `GET /api/v1/admin/transactions`, optionally filtered by `user_id`, `type`, `status`, `from`, and `to` (date range), with `per_page` from 1 to 100. This endpoint returns transaction references and associated user identity for finance reconciliation, but never the idempotency key. The `balance_after` snapshot is for this permission-protected financial audit only; regular users must not receive it through their API or general logs.
- Wallet top-ups use `POST /api/v1/auth/wallet/top-ups` with `amount` (integer tomans) and a UUID `Idempotency-Key`. Zarinpal starts disabled by default. For Sandbox, the official docs permit any valid UUID string as the merchant ID; no live merchant account or real payment is needed. Set `PAYMENT_ENVIRONMENT=sandbox`, `ZARINPAL_SANDBOX_MERCHANT_ID` to a generated UUID, and `ZARINPAL_PAYMENT_ENABLED=true`, then enable `zarinpal` through `PUT /api/v1/admin/payment-gateways` (`default_gateway`, `enabled_gateways`, `failover_order`) if the admin settings row has been initialized. `APP_URL` must point to an address reachable by the browser completing checkout: localhost works when that browser is on the development machine; a phone needs the backend's LAN address (and access to that host/port). Each attempt stores the environment used at initiation so an outstanding callback continues to verify with the matching merchant and endpoint if the global environment changes. Use separate production credentials only after provider approval; never enable production as a fallback. Admins with `view transactions` can inspect purchase reconciliation at `GET /api/v1/admin/payment-orders`; idempotency keys are not returned. A callback is not trusted as payment proof: `Status=OK` requires server-side `Verify`; `Status=NOK` is checked with server-side `Inquiry`, where `IN_BANK` remains pending, `FAILED`/`REVERSED` may fail the attempt, and `PAID`/`VERIFIED` still require `Verify`.
- The current Zarinpal Sandbox flow was verified with `currency=IRT`: send the same integer toman amount in both the request and verify call. The generic connection guide describes the verify amount in rials, but multiplying by 10 returned provider error `-50` in Sandbox; using the original IRT amount verified successfully. Confirm this behavior against the current Production contract before enabling live payments. Requests set `metadata.auto_verify=false` so server-side verification remains under backend control and successful payments without a callback remain eligible for recovery. The scheduled `payments:reconcile-zarinpal` command checks Zarinpal's `unVerified` list every ten minutes, then uses `Inquiry` for up to 100 locally known pending authorities per environment, no more often than every 30 minutes per attempt. Only `PAID`/`VERIFIED` inquiry results trigger server-side `Verify`; inquiry alone never credits the wallet or activates a subscription. The `unVerified` provider list itself is limited to its latest 100 payments. An initiation timeout before any authority was saved cannot be safely correlated automatically and requires manual reconciliation.
- Gateway failover proceeds only after an adapter reports a definitive rejection or a retryable result that confirms no payment was accepted. Ambiguous timeouts/API responses remain `initiation_unknown` and never trigger a second gateway attempt. Since only Zarinpal Sandbox is currently configured, no cross-provider failover has yet been exercised.
- Manual Sandbox scenarios verified: successful wallet top-up; successful subscription purchase using a partial discount and a mixed wallet/gateway payment; definitive cancellation refunded the wallet contribution once and released the discount for retry; retry consumed the discount and activated one subscription; a 100% discount completed without creating a gateway attempt; a paid transaction with an intentionally unreachable callback was recovered through `Inquiry` and `Verify` with exactly one wallet credit, and a second reconciliation run created no duplicate. Automated project tests were not run during those manual scenarios. Separate automated tests use fake provider responses and cover selected callback/reconciliation paths, including MySQL concurrency cases documented in [docs/testing-roadmap.md](docs/testing-roadmap.md); they do not substitute for repeatable provider Sandbox verification. Live provider callback behavior, cross-provider failover (only Zarinpal is configured), and Production behavior remain unverified.
- Inactivity-based account deletion is opt-in and requires a verified phone number. Users may choose 6, 12, or 18 months without activity. The API rejects activation until Melipayamak SMS is configured. Set `MELIPAYAMAK_INACTIVITY_WARNING_BODY_ID` to a template whose first argument is the user's name and second argument is the 30-day recovery period. After the SMS warning is accepted by the provider, a 30-day recovery period begins. Logging in or disabling the setting cancels the pending deletion. Failed delivery does not start the grace period and is retried by the scheduler.
- Laravel's scheduler must run for expiry cleanup and inactivity notifications/deletion. On a server, configure the standard once-per-minute `php artisan schedule:run` cron entry. The inactivity processor runs daily at 02:00 UTC; expired device sessions are pruned hourly. For local development, use `php artisan schedule:work`.
- `POST /api/v1/auth/profile/photo` accepts an authenticated multipart `photo` upload (JPEG, PNG, or WebP; up to 5 MB).
- Authenticated routes: `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `GET /api/v1/auth/devices`, and `DELETE /api/v1/auth/devices/{deviceId}`.

Apply the migrations with `php artisan migrate` and run `php artisan storage:link` once to serve profile images. For real SMS delivery, set `MELIPAYAMAK_ENABLED=true`, configure `MELIPAYAMAK_API_URL` with the tokenized shared API URL and set `MELIPAYAMAK_OTP_BODY_ID`; treat the complete URL as a secret.

While SMS is disabled, local authentication can be tested without sending a message. Set `APP_ENV=local`, `MELIPAYAMAK_ENABLED=false`, and `MELIPAYAMAK_LOCAL_LOG_ENABLED=true` in the backend `.env`, then restart the backend. The generated OTP is written to `storage/logs/laravel.log` and is not included in the API response. Read the latest log entries with `Get-Content storage\logs\laravel.log -Tail 30`. Register a new phone first, then use the same account to test login. Local OTP logging is ignored outside the `local` environment; do not enable it in shared or production environments.

OTP queue support is implemented but disabled by default. Local log delivery stays synchronous. Enable queued OTP delivery only after real SMS credentials/templates are configured, the queue tables are migrated, and a persistent worker is running: set `SMS_OTP_QUEUE_ENABLED=true`, choose a persistent `QUEUE_CONNECTION` such as `database` or `redis`, refresh Laravel's configuration cache if used, then run the matching worker, for example `php artisan queue:work database --queue=sms --timeout=20`. Restart long-running workers after configuration changes with `php artisan queue:restart`. The application queues OTPs only when Melipayamak is enabled, its shared URL and OTP template are configured, and the selected connection uses a persistent driver (`database`, `redis`, `sqs`, or `beanstalkd`); otherwise it keeps the synchronous path. OTP queue jobs are encrypted, retried up to three times with backoff, and expired or superseded codes are not sent. If all attempts fail, the OTP is invalidated and the failure is recorded in Laravel's failed-jobs store and log; request a fresh code rather than retrying that failed job. A queue worker must be supervised and monitored in production. For the initial Ubuntu setup on ArvanCloud, see [the Scheduler and Worker operations guide](docs/deployment/arvancloud-ubuntu-operations.md) and its Supervisor/Cron templates under `deploy/ubuntu`.

OTP values are hashed in the database. Device tokens use a sliding 30-day inactivity expiration stored in each token's `expires_at`.

For local device access, `SERVER_HOST=0.0.0.0` and `SERVER_PORT=8000` are configured in `.env`, so start the API with `php artisan serve`. Point the mobile app's `EXPO_PUBLIC_API_URL` to the computer's reachable LAN address. These settings expose the development server to devices on the local network; do not use `artisan serve` as a production server.
