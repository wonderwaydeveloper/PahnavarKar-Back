# PahnavarKar Backend

Laravel backend for the PahnavarKar mobile application, Persian-language public website, and Inertia/React admin panel. It provides OTP authentication, subscriptions, wallet and payment workflows, and permission-protected administration.

## Mobile authentication API

The mobile OTP flow uses Laravel Sanctum bearer tokens and Melipayamak SMS:

- `POST /api/v1/auth/otp/send` accepts `phone` and `type` (`login` or `register`). The mobile flow always requests a `login` OTP; the same neutral response is returned for existing and new phone numbers.
- `POST /api/v1/auth/otp/verify` accepts the same phone/type, a six-digit `code`, a UUID `device_id`, and the user's name when required. Existing users receive a session. For a new number, a valid OTP without a name returns `{"status":"profile_required"}`; send the same OTP with a name to complete registration and receive a session.
- Authenticated account management is available through `PATCH /api/v1/auth/profile`, `POST /api/v1/auth/profile/phone` (new phone plus a fresh login OTP), and `DELETE /api/v1/auth/account` (fresh OTP required). Deletion is blocked while payment orders or attempts are unresolved, or a withdrawal is pending/awaiting payout; the same guard applies to inactivity-based deletion. Once clear, deletion revokes tokens and removes the user's associated records.
- Admins with user-management permission can apply either a full suspension or selected capability restrictions. Full suspension can be manual or expire at a selected date/time (preset durations: 1, 3, 7, and 30 days); admins choose whether to revoke sessions and tokens. Preserved sessions cannot make ordinary authenticated requests until reactivation, but the user can still log out; revoked sessions are not restored. Capability restrictions can independently cover financial writes, profile edits, and security changes, with manual or scheduled expiry and the same session-revocation choice. Reads and logout remain available during capability restrictions; account deletion remains separately available. These controls are enforced on the corresponding authenticated API endpoints and do not claim to disable offline/client-only calculator features. A financial restriction also pauses automatic wallet renewal without disabling the user's renewal preference. Status changes and automatic expiry are audited. Automatic wallet renewal is paused during full suspension and resumes after reactivation.
- The authenticated notification inbox is available through `GET /api/v1/auth/notifications` with optional `category`, `read`, `page`, and `per_page` filters; `GET /api/v1/auth/notifications/unread-count` returns unread and read counts, while `POST /api/v1/auth/notifications/{id}/read` and `POST /api/v1/auth/notifications/read-all` update read state. Users can soft-delete an inbox item with `DELETE /api/v1/auth/notifications/{id}` or all read items with `POST /api/v1/auth/notifications/read/delete`; `POST /api/v1/auth/notifications/restore` accepts the returned `undo_token` to restore that user's deletion batch for 30 seconds. Deletion never removes another user's inbox item or the admin announcement record. Notifications are persisted independently of push permission and categorized as account access, security, finance, subscription, service, or announcement; normal/important/urgent priority is separate. Account suspension and partial restrictions create inbox records. Suspension pushes use a generic message and snapshot registered device tokens before optional session revocation, so private reason details are not exposed in OS notifications.
- Users with the `manage notifications` permission can publish immutable official announcements from `/admin/announcements`. Publishing targets accounts that exist at publication time, records the recipient count and publisher, then queues idempotent inbox delivery. Optional device Push is explicitly opt-in per announcement and defaults off. Delivery status is visible in the admin history. Run `php artisan db:seed --class=RolePermissionSeeder` after deployment to add the permission to the existing Owner/Admin role assignments, and ensure the queue worker is running for announcement fan-out and Push delivery.
- Before enabling the notification inbox and official announcement panel in production, apply the new schema with `php artisan migrate --force`, then run `php artisan db:seed --class=RolePermissionSeeder` to grant the new permission to Owner/Admin. The inbox and announcement migrations are `2026_10_29_130000_create_user_notifications_table` and `2026_10_29_131000_create_official_announcements_table`.
- Each authenticated device session stores the operating-system platform, device name, and device model separately, and only one token is retained per device. At most three active device sessions are allowed. Tokens expire after 30 days without an authenticated request; authenticated API activity slides the expiry forward. Expired sessions are pruned hourly by the scheduler and opportunistically during session listing and new logins. A session is labeled stale after seven days without activity but remains revocable before expiration.
- Roles and permissions use Spatie's `web` guard for both web and Sanctum-authenticated users. After applying migrations, run `php artisan db:seed` to create the Owner, Admin, and User roles, baseline permissions, and two unprivileged bootstrap accounts. Existing users without a role, new OTP registrations, and newly created bootstrap accounts receive only the least-privileged User role. `AdminAccountsSeeder` never assigns Owner or Admin and preserves roles assigned explicitly later. Admin web login is available at `/admin/login` and uses OTP for verified phone numbers; only users with the Owner or Admin role can authenticate into the panel. Promote an account only from a trusted server shell after verifying the account ID and phone verification, using `php artisan admin:assign-role 12 Owner` (or `Admin`); the command asks for confirmation. The application never promotes accounts automatically.
- The web app includes a Persian RTL marketing homepage at `/` and an Inertia v3/React admin panel with OTP login and a session-authenticated `/admin` dashboard. The homepage catalog mirrors the mobile app's current `TOOL_DEFINITIONS` and legal categories; subscription durations and prices are rendered from `config/plans.php`. Both are styled with Tailwind CSS, use the locally bundled Shabnam WOFF2 family, share the mobile app's turquoise default palette, and support light, dark, or system color themes saved in the browser; the panel dashboard remains role- and permission-scoped. Admin web pages currently cover the dashboard, users, roles, transactions, withdrawals, discount codes, official announcements, settings, profile, and two-factor authentication. The API remains a separate interface, primarily for the native mobile client; the planned admin-subdomain deployment should use same-origin Laravel/Inertia web routes rather than browser calls to a separate API host.
- Shabnam WOFF2 files include Persian-digit glyphs. Shabnam redistribution must remain within the project's separately obtained FontNegar license.
- User activity logs record only dirty name/profile-photo changes; phone changes create a marker-only audit in the same transaction as the phone update, never the phone value. Financial model logs use explicit allowlists and exclude idempotency keys, provider references, redirect URLs, and payout/review details. Runtime plan, wallet, site-content, and payment-gateway setting changes are audited with explicit manager attribution and allowlisted fields; provider credentials are never stored or logged through these settings. Subscription lifecycle audit and push listeners are auto-discovered once, avoiding duplicate records or notifications. Role changes are audited explicitly by the Owner-only web user-access action, trusted console command, OTP registration, and default-role seeders; those entries also exclude phone numbers, OTPs, tokens, and other authentication secrets. Activity records older than 365 days are removed daily at 03:00 UTC by Laravel's scheduler. Production must invoke `php artisan schedule:run` every minute; deployments with multiple scheduler hosts need a shared cache store for overlap locks.
- Plan prices and durations are defined in `config/plans.php`. `GET /api/v1/plans` lists the configured premium plans. The product does not offer a trial period. Authenticated users can inspect their current subscription at `GET /api/v1/auth/subscription`, cancel the active subscription at `DELETE /api/v1/auth/subscription`, and enable/disable wallet-only renewal at `PUT /api/v1/auth/subscription/auto-renew`. Renewal runs every minute after expiry, uses the current plan price, and never falls back to a gateway; if the wallet cannot cover the full amount, renewal is disabled, the subscription ends, and the app records the failure while the backend sends a push notification where available. Cancellation also disables automatic renewal. Paid plans are purchased with `POST /api/v1/auth/subscription/purchase` (`plan_key`, optional `discount_code` and `payment_method`, and a UUID `Idempotency-Key` header); price is resolved server-side from `config/plans.php`. Payment methods are `wallet` (the wallet must cover the entire payable amount), `combined` (uses the available wallet balance and charges the remainder through the gateway), or `gateway` (leaves wallet balance untouched). Older clients that omit `payment_method` retain the combined-payment behavior. `GET /api/v1/auth/subscription/pending-order` restores an open order and its existing redirect URL so the app can resume that same payment. Poll `GET /api/v1/auth/payment-orders/{id}` for the final order/subscription state, or call `POST /api/v1/auth/payment-orders/{id}/reconcile` for a direct Zarinpal inquiry; only provider-confirmed `FAILED`/`REVERSED` results release the order, wallet debit, and discount reservation. If the initiation result is ambiguous and no provider authority was stored, the order remains locked and must not be blindly cancelled or paid again; the app can prepare the order reference and amounts for support follow-up. A payment failure refunds the wallet contribution and releases any reserved discount.
- Subscription quotes include the selected `payment_method`, wallet/gateway split, plan credit, and discount. The Plans screen enables wallet-only payment only when the wallet covers the payable total; combined payment is enabled whenever the wallet balance is positive (if the balance covers the total, the combined quote uses the wallet for the full amount), and gateway payment remains selectable. Purchase revalidates the selected split while locking the user's balance; if it changed after the quote, the request is rejected so the user can review the new amount. Discount codes apply to manual purchase, upgrade, and scheduled plan orders after any upgrade credit; automatic renewal intentionally uses the current undiscounted price and wallet only.
- Expired subscription orders are failed and their wallet debit/discount reservation released only when no gateway attempt exists or every attempt is confirmed failed. Zarinpal inquiry-confirmed `FAILED`/`REVERSED` attempts are finalized by reconciliation. Pending, initiating, or ambiguous provider outcomes remain open for reconciliation/manual review and are never refunded merely because a local timeout elapsed. The expiration command runs every ten minutes with the Laravel scheduler.
- The internal wallet balance and transaction ledger use integer tomans (`TOMAN`); `GET /api/v1/auth/wallet` returns the balance and `GET /api/v1/auth/wallet/transactions` returns the authenticated user's paginated ledger. Wallet credits are only accepted by the trusted `WalletService` after an external payment has been verified; there is no client credit/deposit endpoint. Purchases debit the wallet atomically through the service and require a UUID idempotency key; one-time internal refunds are available for qualifying failed purchases.
- User financial history endpoints (`GET /api/v1/auth/wallet/transactions`, `GET /api/v1/auth/payment-orders`, and `GET /api/v1/auth/wallet/withdrawal-requests`) accept optional `from` and `to` query parameters in `YYYY-MM-DD` Gregorian format. Bounds are inclusive calendar days in `Asia/Tehran`; either bound may be omitted, and the date filter is applied before pagination.
- The withdrawal request and admin-review workflow is implemented but disabled by default. When enabled, users can store a checksum-validated Iranian IBAN through `PUT /api/v1/auth/wallet/bank-account` or choose a bank card for an individual request. Create/list requests at `POST` and `GET /api/v1/auth/wallet/withdrawal-requests`; creation requires `amount`, a client-generated UUID `idempotency_key`, and `payout_method` (`iban` or `card`, defaulting to `iban` for existing clients). Card requests also require a 16-digit `card_number`, normalized from Persian/Arabic digits and validated with the Luhn checksum. IBAN/card values are encrypted at rest, snapshotted on each request, and masked in user responses. Checksum validation does not verify destination ownership, which must be checked by an administrator before payout. Admins with `manage wallet` (Owner and Admin by default) can set the payout mode for new requests in Admin > Settings > Wallet. Manual mode is the default. Automatic mode is intentionally unavailable and rejected by the server until an actual outbound bank-payment provider and verified settlement worker are integrated; the UI is not the security boundary. Each request snapshots its processing mode, so changing the setting affects new requests only. Admins can list requests at `GET /api/v1/admin/wallet/withdrawal-requests`, approve/reject using `/.../{id}/approve` or `/.../{id}/reject`, and record an externally completed transfer at `/.../{id}/paid` with its payout reference. Rejection releases the reserved balance as a separate ledger entry; an approved-but-not-paid request can still be rejected and released. No bank transfer is initiated by the application; the administrator must complete the transfer externally before marking it paid. Limits are 100,000 toman per request and 500,000 toman per day across `pending`, `approved_pending_payout`, and `paid` requests; rejected requests do not count.
- Admins with `view transactions` can browse the paginated, all-user ledger at `GET /api/v1/admin/transactions`, optionally filtered by `user_id`, `type`, `status`, `from`, and `to` (date range), with `per_page` from 1 to 100. This endpoint returns transaction references and associated user identity for finance reconciliation, but never the idempotency key. The `balance_after` snapshot is for this permission-protected financial audit only; regular users must not receive it through their API or general logs.
- Wallet top-ups use `POST /api/v1/auth/wallet/top-ups` with `amount` (integer tomans), an optional `app_return_url`, and a UUID `Idempotency-Key`; the minimum amount is 10,000 tomans (`PAYMENT_MIN_TOP_UP`, default `10000`) and the maximum is `PAYMENT_MAX_TOP_UP`. The mobile app supplies its current Expo return URL, which is validated and saved on the payment attempt so both wallet and subscription callbacks return to that same app session. Accepted URLs use the installed-app `pahnavarkar://payment-return` scheme or an Expo `exp(s)://` URL on a private/local or Expo host. Older clients use `PAYMENT_APP_RETURN_URL` as a fallback. `GET /api/v1/auth/wallet` returns both amount limits. The Wallet screen launches the returned gateway URL and can resume/check pending attempts via `GET /api/v1/auth/wallet/pending-top-up`; `POST /api/v1/auth/payments/{id}/reconcile-wallet-top-up` performs an owner-scoped Zarinpal inquiry, verifies confirmed payments, and releases a top-up only after the provider confirms `FAILED` or `REVERSED`. `IN_BANK` remains locked to prevent duplicate payments. An ambiguous initiation without a stored provider authority cannot be proven safe to cancel, even if the app did not open a gateway session; it remains locked for support follow-up rather than allowing a potentially duplicate charge. The legacy cancellation endpoint therefore rejects unresolved attempts; age alone does not make an initiation safe to release. Only one standalone wallet top-up may be active per user; a pending, initiating, or ambiguous attempt must be resolved before another can be started. Zarinpal starts disabled by default. For Sandbox, the official docs permit any valid UUID string as the merchant ID; no live merchant account or real payment is needed. Set `PAYMENT_ENVIRONMENT=sandbox`, `ZARINPAL_SANDBOX_MERCHANT_ID` to a generated UUID, and `ZARINPAL_PAYMENT_ENABLED=true`, then enable `zarinpal` through `PUT /api/v1/admin/payment-gateways` (`default_gateway`, `enabled_gateways`, `failover_order`) if the admin settings row has been initialized. `APP_URL` must point to an address reachable by the browser completing checkout: localhost works when that browser is on the development machine; a phone needs the backend's LAN address (and access to that host/port). Each attempt stores the environment used at initiation so an outstanding callback continues to verify with the matching merchant and endpoint if the global environment changes. Use separate production credentials only after provider approval; never enable production as a fallback. Admins with `view transactions` can inspect purchase reconciliation at `GET /api/v1/admin/payment-orders`; idempotency keys are not returned. A callback is not trusted as payment proof: `Status=OK` requires server-side `Verify`; `Status=NOK` is checked with server-side `Inquiry`, where `IN_BANK` remains pending, `FAILED`/`REVERSED` may fail the attempt, and `PAID`/`VERIFIED` still require `Verify`. Apply the payment-attempt return URL schema with `php artisan migrate --force` before deploying this version.
- The current Zarinpal Sandbox flow was verified with `currency=IRT`: send the same integer toman amount in both the request and verify call. The generic connection guide describes the verify amount in rials, but multiplying by 10 returned provider error `-50` in Sandbox; using the original IRT amount verified successfully. Confirm this behavior against the current Production contract before enabling live payments. Requests set `metadata.auto_verify=false` so server-side verification remains under backend control and successful payments without a callback remain eligible for recovery. The scheduled `payments:reconcile-zarinpal` command checks Zarinpal's `unVerified` list every ten minutes, then uses `Inquiry` for up to 100 locally known pending authorities per environment, no more often than every 30 minutes per attempt. Only `PAID`/`VERIFIED` inquiry results trigger server-side `Verify`; inquiry alone never credits the wallet or activates a subscription. The `unVerified` provider list itself is limited to its latest 100 payments. An initiation timeout without a stored authority cannot be correlated automatically; the owner can release it through the cancel-unredirected endpoint when no redirect URL could have reached the app. A still-active `initiating` attempt becomes cancellable only after two minutes; attempts with a stored authority remain subject to provider reconciliation.
- Gateway failover proceeds only after an adapter reports a definitive rejection or a retryable result that confirms no payment was accepted. Ambiguous timeouts/API responses remain `initiation_unknown` and never trigger a second gateway attempt. Since only Zarinpal Sandbox is currently configured, no cross-provider failover has yet been exercised.
- Manual Sandbox scenarios verified: successful wallet top-up; successful subscription purchase using a partial discount and a mixed wallet/gateway payment; definitive cancellation refunded the wallet contribution once and released the discount for retry; retry consumed the discount and activated one subscription; a 100% discount completed without creating a gateway attempt; a paid transaction with an intentionally unreachable callback was recovered through `Inquiry` and `Verify` with exactly one wallet credit, and a second reconciliation run created no duplicate. Automated project tests were not run during those manual scenarios. Separate automated tests use fake provider responses and cover selected callback/reconciliation paths, including MySQL concurrency cases documented in [docs/testing-roadmap.md](docs/testing-roadmap.md); they do not substitute for repeatable provider Sandbox verification. Live provider callback behavior, cross-provider failover (only Zarinpal is configured), and Production behavior remain unverified.
- Inactivity-based account deletion is opt-in and requires a verified phone number. Users may choose 6, 12, or 18 months without activity and must confirm that the remaining wallet balance and access to any active subscription and its benefits will become unavailable after deletion. The API rejects activation until Melipayamak SMS is configured. Set `MELIPAYAMAK_INACTIVITY_WARNING_BODY_ID` to a template whose first argument is the user's name and second argument is the 30-day recovery period. The provider-side template must also state that the remaining wallet balance and active subscription benefits will become unavailable, and explain how to cancel deletion before the deadline. Suggested Persian template: «کاربر گرامی {نام}، به‌دلیل عدم فعالیت، حساب شما تا {مهلت} روز دیگر حذف می‌شود. در صورت حذف، ماندهٔ کیف پول و دسترسی به اشتراک فعال و مزایای آن از دسترس شما خارج می‌شود. برای لغو حذف خودکار، تا پایان مهلت وارد حساب شوید یا این گزینه را در تنظیمات خاموش کنید.» Confirm the exact approved template in the Melipayamak account; changing this documentation does not update the provider's template. After the SMS warning is accepted by the provider, a 30-day recovery period begins. Logging in or disabling the setting cancels the pending deletion. Failed delivery does not start the grace period and is retried by the scheduler.
- Laravel's scheduler must run for expiry cleanup, temporary suspension reactivation, and inactivity notifications/deletion. On a server, configure the standard once-per-minute `php artisan schedule:run` cron entry. Expired suspensions are reactivated every minute; the inactivity processor runs daily at 02:00 UTC; expired device sessions are pruned hourly. For local development, use `php artisan schedule:work`.
- `POST /api/v1/auth/profile/photo` accepts an authenticated multipart `photo` upload (JPEG, PNG, or WebP; up to 5 MB).
- Authenticated routes: `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `POST /api/v1/auth/logout-others` (atomically revokes other sessions while preserving the current session), `GET /api/v1/auth/devices`, and `DELETE /api/v1/auth/devices/{deviceId}`.

Apply the migrations with `php artisan migrate` and run `php artisan storage:link` once to serve profile images. For real SMS delivery, set `MELIPAYAMAK_ENABLED=true`, configure `MELIPAYAMAK_API_URL` with the tokenized shared API URL and set `MELIPAYAMAK_OTP_BODY_ID`; treat the complete URL as a secret.

While SMS is disabled, local authentication can be tested without sending a message. Set `APP_ENV=local`, `MELIPAYAMAK_ENABLED=false`, and `MELIPAYAMAK_LOCAL_LOG_ENABLED=true` in the backend `.env`, then restart the backend. The generated OTP is written to `storage/logs/laravel.log` and is not included in the API response. Read the latest log entries with `Get-Content storage\logs\laravel.log -Tail 30`. Register a new phone first, then use the same account to test login. Local OTP logging is ignored outside the `local` environment; do not enable it in shared or production environments.

OTP queue support is implemented but disabled by default. Local log delivery stays synchronous. Enable queued OTP delivery only after real SMS credentials/templates are configured, the queue tables are migrated, and a persistent worker is running: set `SMS_OTP_QUEUE_ENABLED=true`, choose a persistent `QUEUE_CONNECTION` such as `database` or `redis`, refresh Laravel's configuration cache if used, then run the matching worker, for example `php artisan queue:work database --queue=sms --timeout=20`. Restart long-running workers after configuration changes with `php artisan queue:restart`. The application queues OTPs only when a configured provider is active and the selected connection uses a persistent driver (`database`, `redis`, `sqs`, or `beanstalkd`); otherwise it keeps the synchronous path. OTP queue jobs are encrypted, retried up to three times with backoff, and expired or superseded codes are not sent. A job that reaches a worker after its five-minute OTP expiry is discarded without delivery, so monitor SMS queue age well below that limit. A provider timeout can be ambiguous (the provider may have accepted the SMS before the response was lost); retries use the same OTP and may produce duplicate messages. After all attempts fail, the OTP is invalidated and the failure is recorded in Laravel's failed-jobs store and redacted logs; terminal queue failures are also sent to Sentry when configured. Request a fresh code rather than retrying that failed job. Configure and verify operational alerts and supervise/monitor workers in production; repository tests do not prove Sentry delivery or handset delivery. For the initial Ubuntu setup on ArvanCloud, see [the Scheduler and Worker operations guide](docs/deployment/arvancloud-ubuntu-operations.md) and its Supervisor/Cron templates under `deploy/ubuntu`.

Kavenegar can be configured as an alternate SMS provider with `KAVENEGAR_ENABLED=true`, `KAVENEGAR_API_KEY`, and optionally `KAVENEGAR_SENDER`. Keep the API key only in the server's secret environment; the admin panel never accepts or displays provider credentials. After configuring the secrets and deploying, run `php artisan db:seed --class=RolePermissionSeeder --force` once to grant the new `manage sms providers` permission to the seeded admin roles. Authorized admins can then switch between configured providers at **Admin → Settings → SMS service**; the selection applies immediately to new sends. The Kavenegar adapter uses its documented HTTPS `sms/send.json` API and sends Iranian mobile numbers in local `09...` format.

Admins with `manage sms providers` can send a fixed test message to an entered Iranian mobile number from the same SMS settings page. The endpoint is limited to one send per minute and five per hour per admin and per destination; the full destination is never written to the activity log. Kavenegar uses a fixed non-OTP message. Melipayamak requires a separately approved, no-placeholder test template configured as `MELIPAYAMAK_TEST_BODY_ID`; its text should be «پیام آزمایشی سرویس پیامک پهناورکار؛ نیازی به پاسخ نیست.» Do not reuse the OTP template. A successful provider response means the provider accepted the request, not that handset delivery is confirmed. In local log mode, the action is only logged and no real SMS is sent.

OTP values are hashed in the database. Used and unused OTP rows are retained until one day after `expires_at`, then pruned daily in batches; they are not an authentication or audit history. Device tokens use a sliding 30-day inactivity expiration stored in each token's `expires_at`.

For local device access, `SERVER_HOST=0.0.0.0` and `SERVER_PORT=8000` are configured in `.env`, so start the API with `php artisan serve`. Point the mobile app's `EXPO_PUBLIC_API_URL` to the computer's reachable LAN address. These settings expose the development server to devices on the local network; do not use `artisan serve` as a production server.
